# Security

## Reporting a problem

Open a GitHub issue, or, for something that should not be public yet, use GitHub's private vulnerability reporting
on the repository (Security › Advisories › Report a vulnerability). Say which version (Help › About) and attach the
folder from Help › Create Diagnostic Report if it helps; it is never sent anywhere by itself.

## What the updater verifies

Milan Pro updates itself from GitHub Releases over HTTPS (`src/updater.rs`). Only `github.com`, `api.github.com`
and `*.githubusercontent.com` are ever contacted, redirects included.

1. **Integrity (always):** the installer's SHA-256 must match the release's `MilanPro-<version>-Setup.exe.sha256`
   file (or the API's asset digest, when no signing key is compiled in). The file is hashed again just before it
   runs.
2. **Authenticity (with a signing key):** the `.sha256` file must carry a valid
   [minisign](https://jedisct1.github.io/minisign/) signature, `MilanPro-<version>-Setup.exe.sha256.minisig`, made
   with the maintainer's secret key. The matching public key is compiled into Milan Pro
   (`updater::MINISIGN_PUBLIC_KEY`). When the key is configured, a release whose signature is missing or does not
   verify is refused, and the API digest is no longer trusted on its own. The update dialog says which of the two
   checks applied.
3. **Code signing (Authenticode):** not yet (certificate pending). `release.yml` has the `signtool` step wired; it
   runs only when the certificate secrets exist (below).

Until the key pair exists, `MINISIGN_PUBLIC_KEY` is empty and updates are checked by SHA-256 alone, which proves the
download matches the release but not who published it. This is stated in the update dialog and in README.

## Generating the signing key (maintainer, once)

The key pair is the maintainer's to make; it is never generated by the build.

1. Install minisign (`choco install minisign`, `brew install minisign`, or a release from its GitHub page).
2. Generate a key pair without a password, so the release workflow can sign unattended:

       minisign -G -W -p minisign.pub -s minisign.key

   Keep `minisign.key` out of the repository. Store it somewhere safe (a password manager) as well.
3. Put the public key (the second line of `minisign.pub`, starting with `RW`) into
   `src/updater.rs`:

       pub const MINISIGN_PUBLIC_KEY: &str = "RW...";

   and commit. From the next release on, every build refuses unsigned updates.
4. Add the repository secret `MINISIGN_SECRET_KEY` with the full contents of `minisign.key` (both lines).
   `release.yml` signs `MilanPro-<version>-Setup.exe.sha256` with it and uploads the `.minisig` beside it. Without
   the secret the step is skipped and the release carries no signature.

The first signed release should be published by a build that still has the key compiled in (step 3 before step 4
is fine: a build with the key and no `.minisig` on the release simply refuses that release, so publish in this
order: commit the key, then add the secret, then tag).

## Rotating the key

1. Generate a new pair as above.
2. Replace `MINISIGN_PUBLIC_KEY` with the new public key and release that build **signed with the old key**
   (keep the old `MINISIGN_SECRET_KEY` secret for this one release): installed builds verify it with the old key
   and, once updated, carry the new one.
3. Replace the `MINISIGN_SECRET_KEY` secret with the new secret key. Every later release is signed with it.
4. Destroy the old secret key. A build older than step 2 cannot verify the newer releases; its users install the
   step-2 release by hand (its checksum still matches) and update normally from there.

A compromised key is rotated the same way, except that step 2 cannot be signed with the old key: publish the
step-2 release unsigned, say so in its notes, and ask users to verify its SHA-256 against the release page.

## Code signing (Authenticode)

`release.yml` signs `MilanPro.exe`, `milan-plugin-host.exe` and the installer with `signtool` when these
repository secrets exist:

- `CODE_SIGN_PFX_BASE64`: the certificate and private key as a base64-encoded PFX.
- `CODE_SIGN_PASSWORD`: the PFX password.

Obtaining a certificate is a maintainer action: SignPath Foundation (free for open-source projects) or a paid
service such as Azure Trusted Signing. Until then Windows SmartScreen warns on the installer, and README says
"Code signing: not yet (certificate pending)".

## Other notes

- Crash reports (`%LOCALAPPDATA%\MilanPro\crashes`) and diagnostic reports stay on the machine; "Report on GitHub"
  only opens the new-issue page. Preferences › Update can leave file names and paths out of them.
- Plug-ins (OFX, VST3, CLAP) run in a separate host process (`milan-plugin-host.exe`); a plug-in crash does not take
  the editor down. They are still native code from third parties: install only plug-ins you trust.
